# 二维码 / 条码自动识别 —— 交互与性能设计存档

> 目标工程：`SnowAir/Native`（Win32 + Direct2D + Ling 框架）
> 状态：**第一版已实现**（2026-11-05），链路可跑，档位/悬停/去重阈值待实测调
> 本文记结论、依据与待定参数；实现落点见 §14。

---

## 0. 一句话方案

框选定格后静默扫一遍二维码（可选一维码），命中就在**码上浮一个半透明按钮**；点击出**贴着码的半透明结果卡**，点卡外或 Esc 收回。手动入口（OCR 气泡 / 快捷键 `Q`）全部保留，作为能力边界的兜底。

核心判断：**这个功能的上限不在"猜得准"，而在"猜错的代价≈0"**。截图是一次性、无上下文的动作——没有账号画像、没有历史，能用的信号只有几何和时序。所以不做"意图识别"的承诺，只做降噪。

## 2. 目标 / 非目标

**目标**

1. 框选完就能看到"这里有码"，不需要先想起来去点气泡。
2. 点击后结果贴着码出现，不遮挡画面其余部分。
3. 用户继续画标注、调选区、直接完成，都不被角标干扰。
4. 导出/复制的图里保证没有角标。

**非目标**

1. 不做"理解用户想不想扫"的智能预测，理由见 §3。
2. 不新增常驻图标、不新增轮询、不新增全局钩子。
3. 不做多格式全家桶（DataMatrix / PDF417 / Aztec 暂不做，见 §6.4）。

## 3. 意图模型

### 3.1 四类真实意图

| 意图 | 场景 | 要的结果 | 对功能的要求 |
|---|---|---|---|
| **A 扫码** | 屏幕上看见一个码，想拿里面的链接/文本 | 内容 | 快、准、贴着码 |
| **B 留图** | 截海报/聊天/网页，里面恰好有码 | 那张图 | 完全不打扰 |
| **C 无关** | 桌面图标、页脚支付码、别人头像 | 那张图 | 不可见 |
| **D 编辑** | 要画箭头、打码、裁剪 | 改过的图 | 主动让位 |

### 3.2 信号表（按可靠性排序）

| 信号 | 可靠性 | 说明 |
|---|---|---|
| **选区紧贴度**（四边留白） | ★★★★★ | 用户自己的动作，不是猜。框得越紧 = 越想扫 |
| **停留**（光标在码附近静止 ~400ms） | ★★★ | "看"的代理，会滞后 |
| 码的绝对尺寸 | ★★ | 只说明"扫得动"，不说明"想扫" |
| 内容类型（URL / 文本 / 数字） | ★★ | 只影响卡片，不影响触发（见 §3.3） |
| 前台应用名 `focusAppName_` | ★ | 应用→意图的映射全是偏见，**不用** |
| **负向信号**：开始画标注 / 拖选区 / 直接完成 | ★★★★★ | 意图已被用户否定，立刻退场 |

### 3.3 顺序上问三个问题

- **Q1 能扫吗？** 模块 ≥3px 且解码成功。不满足就静默，不进入意图判断。
- **Q2 想扫吗？** 紧贴度 + 停留 + 负向信号。只决定**档位**，不决定有无。
- **Q3 扫到了干什么？** URL → 复制/打开；文本 → 复制；1D → 只复制。只影响**卡片长什么样**。

> 把 Q3 混进 Q2 是最常见的错误：一旦用"内容值不值得操作"决定触发，就会出现"这个码不出按钮"的神秘行为，用户无法建立心智模型。

## 4. 交互设计

### 4.1 三级档位（连续、可逆、可发现）

| 档位 | 判定 | 视觉 | 用户感受 |
|---|---|---|---|
| **0 静默** | 无码 / 太小解不动 / 录屏·长图·演示 | 无 | 没有这个功能 |
| **1 微点** | 有码，但码占画面小，或选区明显大于码 | 码角 ~5 DIP 半透明圆点，35% 不透明，悬停展开成按钮 | "哦，这能扫"但不抢眼 |
| **2 按钮** | 码贴合选区（四边留白都小） | 半透明按钮直接浮出 | 一步到位 |

**关键**：档 1 是"可发现性"的保险，档 2 是"高效"的兑现。只有档 2 会让 B 场景的用户永远不知道功能存在；只有档 1 则扫码仍要多一步。

**紧贴度用"四边留白"，不用"面积占比 + 近方形"**：后者是给 QR 写的，一维码宽扁（3:1 以上）会被全判到档 1。逐边看留白与格式无关，斜框、偏框都能正确反映。

### 4.2 悬停细则

- 粘滞区：符号包围盒外扩 **24 DIP**，按钮自身算在区内；
- 淡出延迟 **~150ms**，给"穿过空隙"留时间；
- 滞回：进 24 DIP、出 36 DIP，防手抖闪烁；
- 解码只在框选定格时做**一次**，悬停只做矩形距离比较（微秒级），不新增解码。

### 4.3 结果卡

- 贴着码出现（不盖满选区），半透明底 + 内容 + 复制按钮；
- URL 才给"打开链接"（沿用 `ToolQrcode` 现有的 Ctrl+点击逻辑）；
- 多码时**高亮来源符号的包围盒**——点错了用户一眼看得见，比任何猜测都有效；
- 点卡外或 Esc 收回。

### 4.4 何时藏（状态机）

| 状态 | 角标 |
|---|---|
| 选了绘图工具（`annotLive`） | 藏 |
| 拖选区 / 拖边角中 | 藏，定格后重扫 |
| 录屏（Video）/ 长截图（Long）/ 演示画布（demo） | 不生成 |
| 卡片已打开 | 保持（标记"当前这个"） |
| 选区变化 | 重扫，位置跟着码走 |

## 5. 多码

**不做数量门槛**——点击本身就是意图，系统不必猜是哪一个。数量只影响"怎么显示才不吵"。

| 规则 | 做法 |
|---|---|
| 去重 | 内容相同 → 合并成一个按钮，标 `×N`（重复水印、九宫格海报） |
| 升档 | 多码时覆盖率分母从"整块选区"改为"**所有码合计面积**"，达标则每个都升档 2 |
| 降级 | 同屏可点符号 > ~5 个 → 全部退回微点，或按空间聚合成"3 个码"的组角标，点开列表卡 |
| 碰撞 | 角标锚在各自包围盒角外 6–8 DIP，碰撞时推开；**一维码锚在右侧外侧，绝不压在条上**（会盖住静区和尾部） |

> 超过可读上限就降级的理由不是猜意图，是**可选择性**：8 个半透明按钮摆一起，用户已经无法在其中做选择，那不是交还选择权，是丢回认知负担。人的同时可分辨选项约 5±2。

## 6. 格式范围

### 6.1 白名单

**QR + 7 种常用 1D**：`Code128 / Code39 / EAN-13 / EAN-8 / UPC-A / UPC-E / ITF`。

`Codabar / Code93 / DataBar / DataBarExpanded` 先不开——每个都是额外的扫描线工作量，截图场景极少见；1D 又没有 QR 的强纠错，全开还会扩大误报面（纹理、表格线、条形装饰都可能凑成一条 Code39）。

### 6.2 静区：最容易被忽略、且专挑最有动机的用户

QR 需要 4 模块静区，1D 需要约 10 倍模块宽度的静区。用户手动框码时**极易裁掉静区**，而框得最紧的那个用户恰恰最想扫 → 越认真越失败。

**补法**：解码时把选区**外扩 8–15%** 再喂 ZXing（`screenImg` 是全屏的，不必重新抓屏；不影响导出、不影响角标锚点）。顺带还能救回"框刚好切掉一个定位角"的码。

### 6.3 竖排 1D 是能力盲区

QR 的旋转是自带的（找定位图形），`tryRotate` 主要影响 1D。所以：**QR 任意角度都能自动出角标；竖排 1D 自动路径解不出 → 没有角标 → 用户点不到**。这不是调参能补的，只能靠保留手动入口（`Q` / 气泡），且手动路径跑暴力版（`tryHarder + tryRotate`）一次到位。

### 6.4 以后扩格式

`DataMatrix`（工业标签）、`PDF417`（登机牌票据）、`Aztec`（车票）在 ZXing 里都只是格式位，加是一行的事，代价是自动路径时间线性上升。**锁死当前白名单，扩格式当反馈驱动项。**

## 7. 性能预算

### 7.1 三段成本（估算，需实测校准）

| 环节 | 成本 | 说明 |
|---|---|---|
| `exportSelection` 取像素 | 4K 选区 ~30MB 拷贝，几十 ms | 保存/OCR 都走它，只做一次 |
| ZXing QR only，`tryHarder=false` | 1080p ~5–15ms | 自动路径用这个 |
| ZXing QR + 7 种 1D，`tryHarder=false` | 再加 ~10–30ms | 同一后台线程分两批出角标 |
| 全格式 + `tryHarder` | 几十~几百 ms | **禁止**进自动路径 |

### 7.2 六个杠杆

1. **格式白名单**（§6.1）——收益最大的一刀。
2. **两批出角标**：同一线程先 QR 后 1D，QR 角标 ~20ms 先亮，1D 再补 30ms。不要等两遍都跑完才出。
3. **降采样**：长边缩到 ~1000–1200px 再解码（注意别缩到模块 <3px）。
4. **后台 + 去抖**：选区停稳 ~250–300ms 才扫；拖拽过程中不扫。
5. **代际号**：结果回投 UI 时比对 generation，过期丢弃（沿用 `dq.TryEnqueue` 的投递模式）。
6. **结果缓存**：同一 `maskRect` + 同一 `screenImg` 不重复解码。

### 7.3 结论

**常驻开销为零**（无轮询、无钩子），只在框选定格那一刻多一次后台解码；正常无码截图多 5–15ms 后台 CPU，主线程零卡顿。相对每次截图本来就要付的全屏抓取 + D2D 上传 + 圆角阴影导出，可忽略。

### 7.4 实测与调优（2026-11-05）

第一版是「260ms 去抖 + QR/1D 同一次扫 + 全分辨率解码」，实测（`SNOWAIR_QR_LOG=1`，891×536 选区）：

| 节点 | 第一版 | 现在 |
|---|---|---|
| 框选抬手 → 开始解码 | 266ms（全在等定时器） | **0ms** |
| 解码本身 | 15ms | 15ms（只有二维码时 1D 那遍不跑） |
| 抬手 → 按钮出现 | **~281ms** | **~16ms** |

对照另一套在做的截图工具，差距不在解码器本身，而在三处工程取舍：

1. **它抬手即解**（图像准备丢给 worker，解码串行 worker + 常驻模型），没有任何人为等待。
2. **先只找二维码**，一个都没有才跑一维码检测 —— 一维码是逐行扫的，混在同一次里会让最常见的"就一个二维码"白付那份钱。
3. **大图先缩到 1080p**（`sqrt(1920*1080/面积)`，且长边 ≤2560）再把坐标换算回去。

我们照这三条改完，感知延迟从 ~280ms 降到 ~16ms。剩下还能追的是解码器本身：那边用 DNN 检测 + 解码（OpenCV 的二维码模块）和专用条码检测器，对模糊/反光/斜拍比 ZXing 稳，代价是要带 4 个模型文件（~2MB）并引入 OpenCV 依赖。这一步属于"准确率"而不是"速度"，暂不做。

## 8. 落点（按现有代码）

| 环节 | 位置 | 要点 |
|---|---|---|
| 触发 | [WinCap::onUp](../Src/Win/WinCap.cpp#L3036) 里 `stage = Adjust` 之后 | 框选定格点 |
| 失效/重扫 | [WinCap::onMaskRectChanged](../Src/Win/WinCap.cpp#L3365) | 现在只处理 `toolOcr`，加上角标作废 |
| 角标绘制 | [CutMask::paint](../Src/Win/CutMask.cpp#L2207) | 与 `paintLabel` 同层；**必须加开关**，否则 OCR 面板的 mirror 会把它叠到识别文字上（[WinCap.cpp:4315-4317](../Src/Win/WinCap.cpp#L4315-L4317)） |
| 命中 | `win->cutMask->hitQrBadge(pos)`，在 [onDown](../Src/Win/WinCap.cpp#L2651) 顶部与 `onInfoDown` 并列 | 点卡外收回 |
| 结果卡 | 改造 [ToolQrcode](../Src/Tool/ToolQrcode.cpp#L137) | 从"盖满选区"改成"贴着码的小窗"，`onHitTest` 在外返回 `HTTRANSPARENT`，"点空白点穿并收回"就免费实现 |
| 导出 | 无需改动 | `screenImg + paintShapes` 不含 chrome（[AnnotHost.cpp:2538-2540](../Src/Win/AnnotHost.cpp#L2538-L2540)） |
| 禁用 | `stage == Video / Long`、`demoMode` | 不生成角标 |

### 8.1 三个必须避开的坑

1. **绝不能做成独立窗口**。`ToolQrcode` 是故意不排除出捕获的（用户要能拍下识别结果）；角标反过来——做成窗口就会被别的截图工具、被自己的录屏拍进去。
2. **开始画标注时必须收掉**。用户画箭头指着角标、导出却没有，是"预期落空"，比没有这个功能更糟。
3. **`decodeQrCode` 现在把多结果拼成一条**（`\n`），多码方案必须保留每个码的独立结果和位置（`Barcode::position()` 的四角）。

### 8.2 一个会撞上的冲突

双击空白 = 完成（[WinCap.cpp:2702-2709](../Src/Win/WinCap.cpp#L2702-L2709)）。卡片开着时"点空白收回"会和它打架。**最终处理**：卡片开着时的第一次点击只收卡片，并**吞掉这一下**（不启动选区拖移、不触发双击完成），要点第二下才回到常规操作 —— 单一动作，用户不会"想关卡片却把截图交了"。

## 9. 风险与边界

| 风险 | 应对 |
|---|---|
| 误报 | 有校验位，概率低；白名单收窄 1D 进一步压 |
| 用户就是要截这张带码的图 | 角标不进导出 + 开始标注即退场 + 设置可关 |
| 模糊/反光/被裁静区 | 解码外扩（§6.2）+ 手动入口兜底 |
| 竖排 1D | 承认盲区，靠 `Q` 兜 |
| 性能悬崖 | 自动路径永不进 `tryHarder`；全屏 4K 选区走降采样 |
| 复杂度 | 后台任务 + 悬停状态机 + 阈值调参 + 设置开关 ≈ 比它替掉的气泡项更重。价值必须靠"结果贴着码出"兑现，不能只靠"少一个图标" |

## 11. 验收指标

| 指标 | 定义 | 目标 |
|---|---|---|
| **打扰率** | 角标出现但用户直接完成截图（没点） | < 15% |
| **漏出率** | 码在选区内且可解码，用户却去点了手动入口 | < 5% |
| 主线程卡顿 | 框选定格后的最长同步阻塞 | 0（解码全在后台） |
| 误报 | 角标出现但用户点开后发现内容无意义 | 记录即可 |

两个指标互相对冲：收紧档 2 降打扰率、放宽档 1 降漏出率，正好用来定阈值。

## 12. 分期

**P0（先跑通链路，不调参）**
框选定格 → 后台 QR-only 快速解码 → 单码/多码都在码角出"按钮"（不做微点、不做悬停）→ 点击复用现有 `ToolQrcode` 面板 → 点空白/Esc 收回。
*不含*：1D、紧贴度分档、去重、密度降级、设置开关。

**P1（补完体验）**
1D 白名单 + 解码外扩 + 两批出角标；三级档位与悬停；结果卡改贴码；多码去重/碰撞/降级；设置开关。

**P2（打磨）**
来源高亮、列表卡、点击率校准（长期意图）、参数实测调优。

## 13. 未采纳的方案

| 方案 | 未采纳原因 |
|---|---|
| 只用面积占比阈值 | 会漏掉最该显示的：4K 选区里 600×600 的码只占 4.3%，但那正是要扫的 |
| 只用"接近方形" | 一维码宽扁，全被误判到最低档 |
| 按码数量决定显示与否 | 点击本身就是意图；多码是常见场景（付款页、聊天记录） |
| 按前台应用名猜意图 | 全是偏见，浏览器里也可能在存海报 |
| 全悬停（不做常显） | 发现性归零，用户永远不知道有这功能 |
| 按钮做成独立窗口 | 会被别的截图工具和录屏拍进去 |

## 14. 第一版实现（2026-11-05）

### 14.2 与设计稿的差异

1. **没做三级档位**：目前所有可解码的码都直接给按钮（尺寸下限也没设）。原因：先看真实体感——角标本身已经很小（36 DIP、实色绿、贴着码中心摆），过多再降级比一开始就藏起来容易判断。
2. **没做悬停展开**：同上，先看"常显会不会嫌多"。
3. **没做密度上限**：只做了**同内容去重**（重复水印/九宫格海报）。
4. **没做解码外扩（静区）**：框得太紧导致解不出码的情况目前只能靠手动入口兜。这是下一步最值得先补的一条。
5. **没有设置开关**：默认常开，先看反应。
6. **按钮改成了实色**：第一版用的是半透明深色（85% 不透明），实测在黑白二维码上几乎看不见 —— 半透明色落在模块上会被吃掉一半，看着像没渲染。
   现在是**实色绿（#2FB24F）+ 纯白字形 + 一点投影**，和选框同色系；尺寸固定 36 DIP，压在码的正中心，不跟码放大。
   注意：**不要用 `ToolbarChrome::paintInfoBar` 画它** —— 那条路是"2× 超采样位图再缩回来"，给半透明栏用的，实色填进去会被混合成灰色。直接 `FillRoundedRectangle`。
7. **URL 单击直接打开并退出截图**：卡片里的链接点一下就交给默认浏览器，然后关掉截图会话（用户点链接就是为了去看它，留着覆盖窗只会挡在新标签页前面）。拖选文本不触发 —— 那是想复制。
8. **卡片没有标题**：早期版本有一行「QR Code / EAN-13」，后来试过加一条标题底色带，最后都去掉了 —— 用户点按钮本来就知道自己在看码，多一行只占高度。现在卡片只有正文 + 右上角复制钮，高度 80 DIP。

### 14.3 卡片：不抢焦点的浮层窗口（2026-11-05，架构修正）

第一版把结果卡做成普通置顶小窗，踩了两个坑：**点它会抢焦点**，而卡片又把收到的按键全转发给 `WinCap::onKey` —— 按到绑了命令的键就真的执行（按到文字识别就弹出「正在识别…」）；同时它和识别面板两块窗口互不知情，可以叠在一起。

中途试过把卡片改画在选区 chrome 层里，结果更糟：光标、命中、折行、图标居中每一项都得在绘制层里重写一遍，反复出现"看着没变/样式不对"。

最终回到窗口，但这次是对的：

- **`WS_EX_NOACTIVATE`**：点卡片不抢焦点，键盘始终留在截图窗口 —— 所以**没有任何按键转发代码**（那条转发正是误触发的根因）。
- **内容是框架控件**：正文是只读 `TextBox`、复制是 `Button`。光标（手型只在正文文字/按钮上）、停悬底色、命中判定、折行全部由控件负责，不再手搓。
- **气泡外壳走同一个渲染器**：`ToolbarChrome::paintPropBubble` —— 圆角、45° 尖角、描边与工具栏属性气泡逐像素同源（尖角半宽 = 尖角高度）。注意它内部会切 2× 超采样目标，所以只能画在**卡片自己的**画布上，不能画在选区的 swap chain 画布上。
- **位置**：默认以按钮为中心左右居中、上方弹出、尖角对准按钮中心；贴边时横向避让、上方放不下翻到下方（箭头翻转）。
- **互斥**：结果卡与识别面板都挂在同一选区上，开卡前收识别面板 —— 这是"同时只有一个结果浮层"的状态规则。

代价：卡片正文不能拖选（只读文本框仍可点选，但窗口不激活所以没有键盘焦点），复制走右上角按钮。

### 14.4 已知边界

- 竖排一维码在自动预扫里解不出（`tryRotate` 关着）→ 没有角标，只能走 `Q` 手动。
- 一维码只认正对/近正对的，斜着贴的条码会漏。
- 角标和卡片都进不了导出（chrome 层），但也意味着**用户想连码一起截走时它们不会出现在图里** —— 这是设计目标，不是 bug。
- 卡片正文超出约三行会被裁掉（没有滚动条），长内容建议复制。
